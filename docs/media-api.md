# Phase 6: car media and Cloudflare R2

## Configuration

Set `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_BUCKET`, and `R2_PUBLIC_BASE_URL` in `.env`. The access key needs object read/write/delete permissions on the selected bucket. `R2_PUBLIC_BASE_URL` is the HTTPS origin (or path prefix) serving public objects, preferably a custom domain. The API starts without these settings, but media operations return 503 until configured. `npm run r2:ping` checks bucket access with `HeadBucket` and does not write an object.

Configure bucket CORS for the admin site's exact origin, method `PUT`, and header `Content-Type`. In Cloudflare R2 → bucket → Settings → CORS policy, add a rule such as `{ "AllowedOrigins": ["http://localhost:3001"], "AllowedMethods": ["PUT"], "AllowedHeaders": ["Content-Type"] }`; add the production admin origin when deployed. The browser sends the exact `Content-Type` returned by presign. The API's `CORS_ORIGINS` does not configure bucket CORS. `npm run r2:check-cors` tests the browser preflight without writing an object; pass another origin as `npm run r2:check-cors -- https://admin.example.com`. `npm run r2:smoke` creates a temporary object through a presigned URL, verifies it with `HeadObject` and public GET, then deletes it in `finally`.

## Upload flow

All routes require a Supabase bearer token and the indicated application permission.

1. `POST /api/v1/admin/media/presign` (`media.create`) with `{ "carId": "uuid", "type": "image", "mimeType": "image/jpeg", "sizeBytes": 12345 }`. Returns `storageKey`, `uploadUrl`, `method: "PUT"`, `headers`, `expiresIn: 300`, and `publicUrl`. The key is generated by the server; filenames from the client are ignored.
2. Browser performs a direct `PUT` to `uploadUrl` with the file as body and the returned `Content-Type` header. Do not send the Supabase bearer token to R2.
3. `POST /api/v1/admin/cars/:id/media` (`media.create`) with `{ "storageKey": "...", "type": "image", "mimeType": "image/jpeg", "sizeBytes": 12345, "altText": "...", "isCover": true }`. The API checks the key belongs to the car, reads object size and MIME from R2 with `HeadObject`, then stores metadata in PostgreSQL. A successful upload is not visible on the site until this request succeeds.

Images: JPEG, PNG, WebP, AVIF, maximum 10 MB each and 10 active images per car. Videos: MP4 or WebM, maximum 100 MB each. Maximum 20 active media records per car. The first image becomes cover automatically; only an image may be cover. Optional width/height are client metadata and are not independently verified.

## Management

| Route | Permission | Purpose |
| --- | --- | --- |
| `GET /api/v1/admin/cars/:id/media` | `media.read` | Active media in display order |
| `PATCH /api/v1/admin/cars/:id/media/:mediaId` | `media.update` | `altText`, `isCover`, or `sortOrder` |
| `PATCH /api/v1/admin/cars/:id/media/order` | `media.update` | `{ "mediaIds": ["uuid", "uuid"] }`, every active media ID exactly once |
| `DELETE /api/v1/admin/cars/:id/media/:mediaId` | `media.delete` | Remove object and DB record; returns 204 |

Media ID and car ID must match. Public and admin car responses omit media marked for deletion. Deletion first marks the row pending and promotes a replacement cover in a transaction, then deletes the R2 object, then deletes the DB row. If R2 or the final DB transaction fails, repeat the same DELETE request: R2 deletion is idempotent and the pending row remains available for retry. Operators can run `npm run media:retry-deletes` to finish all pending deletions after a failure; the command logs `media.delete_recovered` with no actor. A failed confirmation can leave an unregistered R2 object; operators should periodically reconcile bucket keys with `car_media.storage_key` and remove old unregistered objects. Do not apply a blanket age based lifecycle rule to the shared `cars/` prefix because registered media uses the same prefix.

Audit actions are `media.create`, `media.update`, `media.delete`, `media.cover_change`, and `media.reorder`. Swagger documents the routes at `/api/docs`.
